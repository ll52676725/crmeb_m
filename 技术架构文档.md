# CRMEB电商系统后端技术架构文档

## 一、项目概述

CRMEB是一款开源的电商系统，采用前后端分离架构。后端基于Spring Boot框架开发，支持微信公众号、小程序、H5、APP等多种渠道。

### 1.1 技术栈

| 技术 | 版本 | 说明 |
|------|------|------|
| JDK | 1.8+ | Java开发环境 |
| Spring Boot | 2.2.6.RELEASE | 基础框架 |
| MyBatis Plus | 3.3.1 | ORM框架 |
| MySQL | 5.7+ | 关系型数据库 |
| Redis | 5+ | 缓存/分布式锁 |
| Swagger | 2.9.2 | API文档 |
| Druid | 1.1.20 | 数据库连接池 |
| Hutool | 4.5.7 | 工具类库 |
| FastJSON | 1.2.83 | JSON处理 |

### 1.2 模块结构

```
crmeb_m-03/
├── crmeb-common/          # 公共模块
```

#### 订单状态定义

| 状态值 | 状态名称 | 说明 |
|--------|----------|------|
| 0 | 待发货 | 已支付，等待商家发货 |
| 1 | 待收货 | 已发货，等待用户确认收货 |
| 2 | 待评价 | 已收货，等待用户评价 |
| 3 | 已完成 | 交易完成 |

#### 退款状态定义

| 状态值 | 状态名称 | 说明 |
|--------|----------|------|
| 0 | 未退款 | 正常状态 |
| 1 | 申请中 | 用户申请退款，等待审核 |
| 2 | 已退款 | 退款完成 |
| 3 | 退款中 | 退款处理中 |

### 3.3 支付交易架构

#### 支付方式支持

| 支付类型 | 标识常量 | 支付渠道 | 说明 |
|----------|----------|----------|------|
| 微信支付 | PAY_TYPE_WE_CHAT | 公众号/小程序/H5/APP | 主流支付方式 |
| 余额支付 | PAY_TYPE_YUE | - | 用户余额支付 |
| 支付宝 | PAY_TYPE_ALI_PAY | H5/APP | 支付宝支付 |
| 零元付 | PAY_TYPE_ZERO_PAY | - | 0元订单 |

### 3.6 订单拆分(拆单)设计

#### 当前版本现状

**重要说明：本版本(CRMEB-JAVA-KY-v1.3.4)为单商户模式，未实现传统意义上的拆单功能。**

从 `OrderServiceImpl.createOrder()` 方法的实现可以看到：

```java
// 只生成一个订单号
String orderNo = CrmebUtil.getOrderNo("order");

// 只创建一个 StoreOrder 对象
StoreOrder storeOrder = new StoreOrder();
storeOrder.setOrderId(orderNo);

// 所有商品存入同一个订单的 StoreOrderInfo 列表
for (OrderInfoDetailVo detailVo : orderInfoVo.getOrderDetailList()) {
    StoreOrderInfo soInfo = new StoreOrderInfo();
    soInfo.setOrderNo(orderNo);
    // ...
}
```

**结论：所有商品生成一个订单，不支持按商家、仓库、配送方式自动拆单。**

#### 系统中的"类拆单"场景

虽然没有传统拆单，但系统在以下场景有类似拆分的设计：

##### 1. 订单类型区分

| 类型值 | 类型名称 | 字段 | 说明 |
|--------|----------|------|------|
| 0 | 普通订单 | `StoreOrder.type` | 默认类型 |
| 1 | 视频号订单 | `StoreOrder.type` | 微信视频号订单，有特殊处理逻辑 |

视频号订单的特殊处理：
- 预下单时自动关闭余额支付和到店自提
- 快递查询时有特殊逻辑
- 使用 `ShopOrderVo` 和 `ShopOrderAddVo` 作为请求参数

##### 2. 配送方式区分

| 类型值 | 配送方式 | 字段 | 说明 |
|--------|----------|------|------|
| 1 | 快递配送 | `StoreOrder.shipping_type` | 需要收货地址、计算运费 |
| 2 | 门店自提 | `StoreOrder.shipping_type` | 需要选择门店、生成核销码 |

**快递配送 (shipping_type=1) 流程：**
```
用户选择收货地址 → 计算运费 → 生成物流单号 → 商家发货 → 用户收货
```

**门店自提 (shipping_type=2) 流程：**
```
用户选择自提门店 → 生成核销码(verify_code) → 用户到店 → 商家扫码核销
```

##### 3. 营销活动订单限制

从代码中可以看到，**营销活动商品不支持混合购买**，每次只能购买一种活动商品：

```java
// 预下单时只取第一个商品的类型
if (orderInfoVo.getOrderDetailList().get(0).getProductType()
    .equals(Constants.PRODUCT_TYPE_NORMAL)) {
    // 普通商品处理逻辑
}

// 活动商品单独处理
if (storeOrder.getSeckillId() > 0) {
    // 秒杀扣库存 - 只处理第一个商品
    MyRecord skuRecord = skuRecordList.get(0);
}
```

**营销活动订单限制表：**

| 活动类型 | 支持多商品 | 活动ID字段 | 说明 |
|----------|------------|------------|------|
| 普通商品 | 是 | - | 支持购物车多商品一起结算 |
| 秒杀 | 否 | `seckill_id` | 每次只能购买一个秒杀商品 |
| 砍价 | 否 | `bargain_id` | 每次只能购买一个砍价商品 |
| 拼团 | 否 | `pink_id` | 每次只能购买一个拼团商品 |

##### 拆单核心逻辑伪代码

```java
/**
 * 拆单处理服务接口
 */
public interface OrderSplitService {
    
    /**
     * 执行拆单
     * @param request 预下单请求
     * @param orderInfoVo 订单信息
     * @return 拆单后的订单列表
     */
    List<StoreOrder> splitOrder(PreOrderRequest request, OrderInfoVo orderInfoVo);
    
    /**
     * 按指定维度分组商品
     * @param items 商品列表
     * @param dimension 拆单维度
     * @return 分组后的商品Map
     */
    Map<String, List<OrderInfoDetailVo>> groupByDimension(
        List<OrderInfoDetailVo> items, 
        SplitDimension dimension
    );
}

/**
 * 拆单维度枚举
 */
public enum SplitDimension {
    MERCHANT,        // 按商家拆分
    WAREHOUSE,       // 按仓库拆分
    SHIPPING_TYPE,   // 按配送方式拆分
    PRODUCT_TYPE     // 按商品类型拆分
}

/**
 * 拆单核心实现
 */
@Service
public class OrderSplitServiceImpl implements OrderSplitService {
    
    @Override
    public List<StoreOrder> splitOrder(PreOrderRequest request, 
                                          OrderInfoVo orderInfoVo) {
        List<StoreOrder> splitOrders = new ArrayList<>();
        
        // 1. 获取拆单维度配置(可配置化)
        List<SplitDimension> dimensions = getSplitDimensions();
        
        // 2. 按拆单维度递归分组商品
        Map<String, List<OrderInfoDetailVo>> groupedItems = 
            recursiveGroupByDimensions(orderInfoVo.getOrderDetailList(), dimensions);
        
        // 3. 为每个分组创建子订单
        String mainOrderNo = CrmebUtil.getOrderNo("order");
        int subIndex = 1;
        
        for (Map.Entry<String, List<OrderInfoDetailVo>> entry : groupedItems.entrySet()) {
            String groupKey = entry.getKey();
            List<OrderInfoDetailVo> items = entry.getValue();
            
            // 创建子订单
            StoreOrder subOrder = createSubOrder(
                mainOrderNo, 
                subIndex++, 
                groupKey, 
                items, 
                request
            );
            
            splitOrders.add(subOrder);
        }
        
        // 4. 如果是多商户/多仓库场景，需要创建主订单
        if (splitOrders.size() > 1) {
            StoreOrder mainOrder = createMainOrder(mainOrderNo, splitOrders);
            splitOrders.add(0, mainOrder);
        }
        
        return splitOrders;
    }
    
    /**
     * 创建子订单
     */
    private StoreOrder createSubOrder(String mainOrderNo, int index, 
                                         String groupKey, 
                                         List<OrderInfoDetailVo> items,
                                         PreOrderRequest request) {
        StoreOrder subOrder = new StoreOrder();
        
        // 子订单号格式: 主订单号_01, 主订单号_02...
        String subOrderNo = mainOrderNo + "_" + String.format("%02d", index);
        subOrder.setOrderId(subOrderNo);
        
        // 解析分组key，提取商家/仓库/配送方式等信息
        parseGroupKey(subOrder, groupKey);
        
        // 计算子订单价格
        calculateSubOrderPrice(subOrder, items, request);
        
        // 设置其他订单属性
        setOrderCommonAttributes(subOrder, request);
        
        return subOrder;
    }
}
```

```
│                     拆单与退款流程整合                                        │
└─────────────────────────────────────────────────────────────────────────────┘

场景1: 用户申请退款(子订单级)
        │
        ▼
┌────────────────────────────────────────────────────────────────────────┐
│  1. 用户选择某个子订单申请退款                                             │
│  2. 校验该子订单状态(已支付、未退款)                                       │
│  3. 设置子订单 refund_status = 1 (申请中)                                 │
│  4. 管理员审核通过后                                                      │
│     ├── 调用支付接口退款(该子订单实付金额)                                 │
│     ├── 子订单 refund_status = 2 (已退款)                                 │
│     ├── 回滚该子订单的库存                                                 │
│     ├── 不影响其他子订单                                                   │
└────────────────────────────────────────────────────────────────────────┘

场景2: 整单退款(主订单级)
        │
        ▼
┌────────────────────────────────────────────────────────────────────────┐
│  1. 用户申请整单退款                                                      │
│  2. 校验所有子订单状态                                                     │
│  3. 逐个处理子订单退款                                                     │
│     ├── 对每个子订单执行退款流程                                           │
│     ├── 或合并退款金额统一退款                                            │
│  4. 更新主订单状态                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

## 五、关键设计要点

### 5.1 分布式锁与并发控制

- 使用Redis实现库存扣减的原子性
- 预下单信息缓存Redis，设置过期时间
- 秒杀/拼团等活动使用Redis队列控制并发

### 5.2 事务处理

- 使用 `TransactionTemplate` 进行编程式事务管理
- 核心操作(订单创建、支付、退款)都在事务中执行
- 支付成功后使用Redis队列异步处理非核心业务

### 5.3 状态机设计

- 订单状态通过 `status` 字段控制
- 退款状态通过 `refund_status` 字段控制
- 所有状态变更都记录到 `StoreOrderStatus` 表

### 5.4 多渠道支付

- 统一支付入口 `OrderPayService.payment()`
- 根据 `pay_type` 和 `is_channel` 区分支付方式和渠道
- 微信支付支持: 公众号、小程序、H5、APP(iOS/Android)
